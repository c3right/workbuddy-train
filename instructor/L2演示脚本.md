# L2 演示脚本｜从局部操作到完整小型业务任务

> 形式：讲师演示，不要求学员现场独立完成。  
> 建议时长：15—20 分钟。  
> 最终交付：**短研究报告**，不生成 PPT。  
> 本 Demo 不联网、不引入 Skill / Connector / subagent / 代码。

---

## 1. L2 要让学员看到什么

L1 解决的是：

> “我会让 Agent 看资料、完成一个明确动作、生成并修改文件。”

L2 要展示的是：

> “我可以把一个边界清楚的小型业务任务交给 Agent，但不是一键交付；先规划、再组织证据、人工把关、再形成报告。”

主线：

```text
完整任务
→ Plan
→ 人工确认计划
→ 证据矩阵
→ 人工 Gate
→ 短研究报告 v1
→ Review
→ 短研究报告 v2
```

---

# 2. Demo 任务

新建一个 WorkBuddy Task，继续使用同一个 `新岚汽车渠道研究项目/` 项目目录。

讲师先说明：

> “这是一个新的完整业务任务，所以我新开一个 Task；但所有资料还是这个项目里的。”

任务定义：

> **基于现有材料，对新岚汽车四个区域的渠道经营压力做一次初步研究判断，回答‘四区是否是同一个问题、客户三个初始假设目前得到多少支持、下一步最值得验证什么’，最终形成一份内部短研究报告。**

不是要给客户最终解决方案。

---

# 3. Step 1｜先 Plan，不执行

切到 Plan（或直接用自然语言说明“先只给计划”）。

建议输入：

```text
我准备基于这个项目目录，做一份《新岚汽车渠道经营问题初步研究报告》。

我希望最后能回答清楚几件事：
1. 四个区域到底是不是同一种渠道经营问题；
2. 每个区域最突出的压力分别是什么；
3. 客户一开始提的三个假设，现在分别有多少证据支持；
4. 哪些地方现在其实证据还不够；
5. 下一步最值得先补什么、查什么。

你可以用项目背景、交接记录、四份区域访谈、区域渠道经营快照.xlsx 和区域经营指标截图.png。

有几个边界先守住：样本不能代表全国；访谈观点和数据事实要分开；不要把相关关系直接写成因果；材料里没有的数字和事实别补；这次也先不做外部搜索。

先别开始写报告，也别改文件。
你先跟我说说准备怎么做、最先要检查哪些口径和风险。
说完计划就停下来，等我确认下一步。
```

## 讲师现场检查 Plan

一个合格 Plan 至少应该包含：

- 先确认项目边界和口径；
- 读取四区访谈并做对比；
- 读取 Excel / 图表，而不是只看访谈；
- 区分事实、观点、假设、待验证项；
- 先做中间分析，再写最终报告；
- 明确样本不能推全国；
- 不直接做因果推断。

如果 Plan 一上来就是“读取后直接写报告”，讲师现场追加：

> “先别急着写最终稿，中间加一步证据整理，我想先看看判断依据站不站得住。”

Plan 通过后，不要只说“按你的建议继续”。明确告诉它下一步只做到哪里：

> **“这个计划可以。先只做证据矩阵，做完停下来，我看过以后再决定要不要写报告。”**

### 教学点

复杂一点的任务，不必第一句就让 Agent 开始写最终成果。

> **先商量怎么做，比做坏以后再返工便宜。**

---

# 4. Step 2｜先生成证据矩阵

确认 Plan 后进入执行。

建议输入：

```text
那先按刚才的计划做第一步分析，暂时别写最终报告。

把关键证据整理到：
03-output/L2-证据矩阵_v1.md

我希望至少能看到这些主题：
- 四区主要经营压力；
- 库存；
- 价格/优惠；
- 总部线索与门店执行；
- 固定成本；
- 县域覆盖与轻量网点；
- 售后服务覆盖。

重要的判断尽量顺手标一下：来自哪个文件、属于数据事实还是访谈/客户说法、还有什么限制或冲突。

做到证据矩阵这一步就停，不要继续写报告。
```

---

# 5. Step 3｜人工 Gate：先检查证据，再批准写报告

打开 `L2-证据矩阵_v1.md`。

讲师不要逐字审稿，只检查 8 个高风险点：

1. **样本边界**：有没有把 12 家样本门店写成全国；
2. **库存**：有没有看出华东明显高、华北相对稳定，而不是写成全国库存问题；
3. **线索**：有没有保留“线索质量 vs 门店首响/跟进”的不同说法；
4. **轻量网点**：有没有保留四区态度和附加条件，而不是简单写成“大家都支持”；
5. **未经证实数字**：有没有把“无效线索接近三成”“明年网点增加 30%”写成事实；
6. **因果**：有没有因为优惠率、零售、库存同时变化就直接下因果结论；
7. **少数观点被放大**：有没有把某一位或少数受访者的说法，升级成某个区域甚至多个区域的共同结论；
8. **证据不足被写成否定结论**：材料不足时，是否误写成“假设不成立”“没有这个问题”。

如果发现可疑点，不要默认它一定错，先让 Agent 回查。例如：

```text
先别写报告，我想让你把证据矩阵里两处再核一下。

第一，线索那部分看看有没有把个别受访者关于首响/跟进的观点，概括成了几个区域的共同问题。
第二，华南“无效线索接近三成”这句话，再确认一下现在有没有把它写得太实；我记得它只是一个受访者的口头估计，也没有底表。

如果需要就先把证据矩阵改掉；如果原来没问题，也直接告诉我为什么没问题。
做完这一步先停。
```

### 教学点

> **人要在关键节点把关，而不是等最终报告做完才发现证据基础错了。**

---

# 6. Step 4｜生成短研究报告 v1

证据矩阵通过后，再批准写报告。

建议输入：

```text
证据矩阵这版可以了。现在基于它和原始材料，帮我出一版内部短研究报告。

文件放到：
03-output/L2-渠道经营问题初步研究报告_v1.docx

我希望大致按这个顺序写：
1. 核心判断；
2. 四个区域的主要差异；
3. 对客户三个初始假设的初步判断；
4. 目前哪些地方证据还不够；
5. 下一步优先验证什么；
6. 样本和方法限制。

正文尽量控制在 1200—1800 字左右，给内部项目会快速看，必要的比较表可以保留。
先说判断，再摆证据；事实、访谈观点和我们的初步判断继续分清楚。
这次只做到问题识别，不要直接给“全国渠道应该怎么改”的最终方案。
排版不用做复杂，清楚好读就行。
```

### 讲师提示

如果 WorkBuddy 对 DOCX 生成表现异常，不要转向 PPT 或现场排查复杂格式。可以直接要求：

> “内容先用 Markdown 写出来也可以，这次我更关心研究判断，格式先别折腾。”

这不是失败。本 Demo 的教学重点是**研究流程与证据控制**。

---

# 7. Step 5｜Review v1

打开报告，重点检查：

- 开头是否真正回答“四区是不是同一个问题”；
- 有没有把某个单一区域现象当成全国主因；
- 对三个客户假设是否区分“现有证据支持到什么程度”和“仍然不知道什么”；
- 有没有把“证据不足”写成“假设不成立”；
- 有没有把少数受访者的观点写成区域或跨区域共性；
- 有没有保留华东、华南、西南、华北的不同结构；
- 下一步验证是否具体；
- 是否明确写了样本限制。

## 预期合理的核心判断

方向应该接近：

> 现有材料不支持把新岚汽车渠道压力归结为单一全国性问题。四区都存在经营压力，但压力形态不同：华东更突出库存结构、价格与盈利；华南更突出促销、线索运营与门店执行；西南更突出服务覆盖和轻量渠道履约责任；华北在库存相对稳定的情况下仍受固定成本、价格竞争和执行效率影响。

不要求逐字一致。

---

# 8. Step 6｜具体反馈，生成 v2

不要说：

> “还是不够好，再专业一点。”

要示范具体反馈，而且不要为了演示修改而强行假设 v1 一定有某个错误。

例如现场看完后，如果确实有下面这些问题，可以这样说：

```text
v1 先保留，不要覆盖。

我看下来有几个地方想让你再检查一下，有问题再改：
1. “总部线索不足”是不是说得太确定了？如果是，改成把四个区域各自的证据并列比较；
2. 西南那部分有没有把“销售触点更近不等于整体渠道效率一定更高”这个边界讲清楚；
3. 下一步验证事项如果还是太泛，就帮我收成 4—5 个下一步可以直接去查的数据或问题。

其他已经没问题的地方尽量别乱动。
新版保存成：
03-output/L2-渠道经营问题初步研究报告_v2.docx
```

如果 v1 已经很好，可以把 Review 重点放在：

- 压缩长度；
- 增加来源提示；
- 把过度断言改为有边界的判断；
- 把下一步验证写得更可执行。

---

# 9. Demo 收口：让学员看到 L1 → L2 的升级

最后只比较两层：

## L1

```text
看一个目录
→ 读一个文件
→ 综合一个文件夹
→ 用样例生成文件
→ Review
→ v2
```

## L2

```text
一个完整业务问题
→ 先规划
→ 多类型材料共同使用
→ 证据矩阵
→ 人工 Gate
→ 研究判断
→ 短报告
→ Review
→ v2
```

讲师收尾一句话：

> **“L2 并不是多会几个按钮，而是开始知道怎样把一个完整工作拆成 Agent 能稳定承担、自己又能控制质量的过程。”**

---

# 10. Demo 明确不做的事

为了避免把第一次培训带偏，本演示不加入：

- PPT 生成；
- 外部 Web 搜索；
- Skill 制作；
- Connector；
- Automation；
- subagent；
- Git；
- CLI；
- Python / npm；
- 复杂数据建模。

这些都不是 L2 Demo 要证明的东西。
