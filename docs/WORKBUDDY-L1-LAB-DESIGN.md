## 1. 培训要解决的问题

第一次培训不以“学会 WorkBuddy 的所有功能”为目标，而要让学员完成一次心智迁移：

```text
网页聊天：我问 → AI 答

        ↓

Agent 工作：
我给目标 + 工作目录 + 资料 + 要求
→ Agent 理解现状
→ 分步骤处理
→ 读写真实文件
→ 我检查结果
→ 继续修改
→ 留下可交付成果
```

第一期毕业标准不是“会写高级 Prompt”，而是：

> 学员能独立打开一个真实工作目录，知道先让 Agent 理解资料，再一步一步推进任务，能检查和修正结果，并保留可回退的版本。

L2“单项任务做出来”只由讲师在同一案例上继续演示，不要求学员现场独立完成。

## 2. 核心教学原则

本 Lab 把 Tencent WorkBuddy 官方高效使用建议转化成可观察的实操动作，而不是单独讲一页“技巧”。

### P1. 清晰表达：做什么 + 有什么 + 怎么样

不要求学员背复杂 Prompt 模板。先建立最小任务表达：

- **做什么**：这一步要完成什么；
- **有什么**：可以使用哪些资料；
- **怎么样**：结果要满足什么要求、放到哪里。

随着练习推进，再自然扩展到：目标 / 输入 / 动作 / 约束 / 输出 / 验收。

### P2. 小步快跑：一次搞定一件事

禁止第一步就下“读完全部资料、做研究、给结论、写报告、做 PPT”的超级任务。

主线按：

```text
理解项目
→ 提取单文件
→ 综合一组材料
→ 生成第一版交付物
→ 检查并修改
```

推进。

### P3. 第一版只是起点

至少安排一次明确的 v1 → review → v2：

- 学员先验收事实、遗漏和格式；
- 明确指出具体差距；
- 让 Agent 修改；
- 不通过“重新写一个超级 Prompt”解决。

### P4. 给样例，而不是堆抽象形容词

Lab 内提供一份“优秀内部项目简报样例”。

学员通过“参考这个样例的结构、信息密度和呈现方式”控制结果，而不是只说“专业一点、像咨询公司一点”。

### P5. 不同任务使用不同会话

同一任务的连续修改留在原会话；明显换任务时新开 Task。

不讲 token / context window，只建立可操作习惯：

> “同一件事继续聊；换一件事，换一张工作台。”

### P6. 默认保留可回退版本

第一次培训不讲 Git。

只培养最朴素但正确的版本习惯：

```text
项目简报_v1.docx
项目简报_v2.docx
```

Agent 修改重要文件前，优先新建版本而不是覆盖原件。

## 3. 借鉴 `Claude Code for Everyone` 的部分

参考其最有效的教学机制，而不是照搬技术栈或原始素材：

1. **单一连续业务故事**：不是五个互不相干的小魔术；
2. **完整项目目录**：背景、混乱输入、模板、附件、输出都在一个工作空间中；
3. **先探索，再行动**：先知道“我接手了什么”；
4. **能力逐步出现**：单文件 → 文件夹 → 模板 → 图片 → 外部信息；
5. **每一步产生真实文件**：学习结果可见、可检查；
6. **前一步成果成为后一步 Context**：学员感受到项目在持续推进；
7. **业务故事本身提供动机**：不是为了练功能而练功能。

不采用：Terminal / Claude Code / Cursor / slash command / custom sub-agent / GitHub / deploy 等内容。

### 版权边界

`Claude Code for Everyone` 当前公开页面标注 CC BY-NC-ND 4.0。本项目：

- 不翻译、改名后再发布其 Basecamp Coffee 原始案例文本；
- 不重新分发其原始课程素材；
- 只借鉴通用教学结构、任务类型和节奏；
- 所有中文业务材料、数据、图片和参考交付物均重新原创。

## 4. 连续案例设定

### 4.1 虚构项目

**项目代号：新岚汽车渠道研究项目（全部为教学用虚构材料）**

场景：

一家虚构汽车企业“新岚汽车”希望了解若干区域市场中经销渠道经营压力和渠道效率问题。咨询团队刚接手项目，已有一批并不整齐的客户材料、内部交接记录、区域访谈摘要和基础数据，但尚未形成一致的问题框架。

学员角色：

> 你刚加入该项目组。先不要急着给客户答案，你需要用 WorkBuddy 把项目接住、把材料看懂、把初步问题理清，并形成一份可以供内部项目会继续讨论的简报。

### 4.2 为什么选择这个场景

- 贴近公司日常咨询 / 行业研究工作；
- 行政岗也能理解“交接、待办、简报、模板”；
- 数据岗能看到 Excel / 图表进入 Agent 工作流；
- 不要求学员具备汽车行业专业知识才能完成；
- 能自然容纳事实、分歧、缺口、样例、版本等 Agent 使用原则。

### 4.3 数据原则

- 所有品牌、人物、经营数字和访谈均为虚构教学数据；
- 不与真实客户资料混用；
- 不要求联网才能完成 L1 主线；
- 故意保留少量不完整、不一致和需要人工判断的信息。

以下内容只能放在 `training/instructor/`，避免 Agent 直接读取“答案”：

- 标准事实清单；

- `CODEBUDDY.md` / `AGENTS.md`；

目的：让学员清楚看到“材料 + 任务表达 + 人工反馈”本身如何影响结果。

## 6. 实操主线

## Exercise 0 — 认识 Agent 工作方式

**形式：讲师引导 + 极短操作**

学员打开 `新岚汽车渠道研究项目/` 作为工作目录。

第一条任务只要求：

> 先查看当前工作目录里有什么，告诉我各目录大致是什么用途。不要修改或生成任何文件。

### 教学点

- Workspace / 工作目录；
- Agent 能“看”项目材料，不只是接收复制进聊天框的文字；
- 第一动作可以是理解，不必立即执行；
- 权限意味着 Agent 真能改文件，所以要区分“先看”和“动手”。

### 成功标志

学员能用自己的话说出：

> “WorkBuddy 不是只回答我，它是在这个目录里围绕任务工作。”

---

## Exercise 1 — 接住项目：先理解，不急着产出

读取 `00-项目背景/`。

建议任务表达：

```text
先阅读 00-项目背景 里的材料。

告诉我：
1. 这个项目要解决什么问题；
2. 已经明确了什么；
3. 哪些事情现在还不能下结论。

暂时不要写正式报告，也不要修改原始文件。
```

### 教学点

- Context = Agent 当前拿到的项目背景与规则；
- 先建立共同理解；
- “不知道 / 暂不能判断”是有效答案；
- 不把第一步变成最终交付。

### 教学原则映射

- P1 清晰表达；
- P2 小步快跑。

---

## Exercise 2 — 单文件 → 结构化提取

读取 `01-项目交接记录.md`。

任务：整理为一个新的工作文件，例如：

`03-output/项目交接整理_v1.md`

至少包含：

- 已知事实；
- 明确待办；
- 项目风险；
- 待确认事项；
- 原文没有明确的信息不得自行补全。

### 材料设计要求

交接记录故意包含：

- 真正重要的事项；
- 普通背景描述；
- 未明确负责人事项；
- 未明确截止日期事项；
- 前任成员的个人判断；
- 一两条与当前任务关联较弱的信息。

### 教学点

- 从“摘要”升级到“按任务提取”；
- 事实 vs 判断；
- 不要让 AI 猜负责人 / 时间 / 事实；
- 生成真实文件。

### 教学原则映射

- P1 做什么 + 有什么 + 怎么样；
- P2 一次完成一个明确动作。

---

## Exercise 3 — 文件夹 → 跨材料综合

读取 `02-区域访谈/` 中四份材料。

先只要求：

```text
阅读这个文件夹里的四份区域访谈。
不要直接写最终报告。

先整理：
1. 多个区域反复出现的问题；
2. 不同区域明显不同的情况；
3. 材料之间存在的矛盾或不同说法；
4. 目前证据不足、下一步需要验证的问题。

结果保存到 03-output/区域访谈综合_v1.md。
```

### 材料设计要求

四份访谈不能只是换地名：

- 2～3 个主题应反复出现；
- 至少 1 个主题存在区域分歧；
- 至少 1 处信息彼此冲突；
- 至少 1 个高价值判断证据仍不足；
- 访谈中混有观点和事实，让学员检查 Agent 是否混淆。

### 教学点

- 文件夹是 Context；
- Agent 可以跨文件找模式；
- “综合”不是简单拼摘要；
- 咨询研究尤其要保留分歧和证据缺口。

### 教学原则映射

- P2 小步快跑；
- P3 第一版不是终点。

---

## Exercise 4 — 参考样例 → 第一版交付物

输入：

- `项目交接整理_v1.md`；
- `区域访谈综合_v1.md`；
- `02-参考样例/优秀内部项目简报样例.docx`。

要求生成：

`03-output/内部项目简报_v1.docx`

### 核心指令思路

不要罗列几十条格式要求，优先使用参考样例：

> 内容以当前项目材料为准；结构、信息密度和表达形式参考样例；不得复制样例中的业务事实。

### 样例文件的设计要求

样例必须：

- 与当前案例业务内容不同，避免 Agent “抄答案”；
- 能明显体现好的标题、摘要、风险、下一步结构；
- 信息密度适合内部快速阅读；
- 不追求复杂美术设计，突出“参考样例控制输出”的效果。

### 教学点

- 参考样例既可以提供格式，也可以提供质量标准；
- 输入文件不只是“事实资料”，也可以是“怎么做”的示范；
- Agent 的结果受 Context 质量显著影响。

### 教学原则映射

- P4 给例子胜过抽象描述。

---

## Exercise 5 — Review → v2，而不是一轮定生死

学员检查 `内部项目简报_v1.docx`。

统一要求至少检查：

- 是否把访谈观点写成确定事实；
- 是否遗漏重要分歧；
- 是否出现原始材料没有的数据 / 人名 / 日期；
- 是否过长；
- 是否真正遵循了参考样例的结构。

然后要求 Agent 修改，但：

> **保留 v1，新建 `内部项目简报_v2.docx`。**

### 教学点

- 验收是人必须承担的工作；
- 给具体反馈，不说“还是不够好”；
- 第一个回答只是起点；
- 重要成果要保留版本。

### 教学原则映射

- P3 多轮调整；
- P6 备份和版本管理。

---

## Exercise 6 — 换任务，换会话

安排一个 5 分钟独立小任务：

> 单独分析 `区域经营指标截图.png`，告诉我图里能直接确认什么、不能确认什么，以及需要结合哪些数据才能进一步判断。

要求学员**新建 WorkBuddy Task**，不要继续在“项目简报”长会话中做。

### 教学点

- 同一任务迭代：留在原 Task；
- 明显换任务：新 Task；
- 新任务仍可使用同一个项目目录；
- 不在已经复杂的旧上下文里一直追加无关任务。

### 教学原则映射

- P5 不同任务使用不同会话。

## 7. L2 讲师演示设计

L2 不另起一个炫技案例，而是继续同一“新岚汽车渠道研究项目”。

讲师演示：

```text
已有背景 + 已整理访谈
+ Excel 基础数据
+ 必要的 Web 补充信息
        ↓
先 Plan
        ↓
人工确认研究步骤 / 口径
        ↓
再执行
        ↓
形成一份短研究简报或 PPT
        ↓
检查证据和结果
```

### 演示目的

让学员看到 L1 之后的自然升级：

- 更多类型资料；
- 更复杂的目标；
- 先规划再执行；
- 数据和外部信息加入；
- 从局部任务升级到较完整的业务交付。

### 明确不演示

- CLI；
- Git；
- subagent；
- 自建复杂 Skill；
- 编程环境安装；
- 底层 Agent 架构。

## 8. 学员最终应该形成的心智模型

课程不要求学员记住大量术语。结束时希望保留下面这张“地图”：

```text
1. 先选对工作目录
        ↓
2. 先让 Agent 看懂已有资料
        ↓
3. 把大工作拆成一个个明确任务
        ↓
4. 说清楚：做什么 / 有什么 / 怎么样
        ↓
5. 必要时给模板或样例
        ↓
6. 让 Agent 真正生成 / 修改文件
        ↓
7. 人检查事实、逻辑、遗漏和边界
        ↓
8. 具体指出问题，继续改
        ↓
9. 重要文件留 v1 / v2，可回退
        ↓
10. 换了一件事，就换一个 Task
```

如果学员只记住这一张图，第一次培训也算达到核心目的。

## 9. L1 通关标准

学员现场不需要独立“做好一个研究项目”。L1 PASS 只要求：

- [ ] 能选择并理解一个 WorkBuddy 工作目录；
- [ ] 知道可以先“只读理解”，而不是直接让 Agent 修改；
- [ ] 能引用单个文件和整个文件夹作为工作资料；
- [ ] 能说清楚一次任务的目标、可用资料和结果要求；
- [ ] 能让 Agent 生成一个真实文件；
- [ ] 能打开并检查该文件；
- [ ] 能指出至少一个具体问题并让 Agent 修改；
- [ ] 能保留 v1 并生成 v2；
- [ ] 知道不同任务应考虑新建 Task；
- [ ] 知道 AI 输出必须由人验收。

不要求：

- 会 Skill 制作；
- 会连接器配置；
- 会自动化；
- 会写代码；
- 会 Git；
- 理解 token / MCP / API 等技术细节。

## 10. 讲师控制点

为了避免培训变成“老师点一下，AI 神奇地产出”，讲师需要刻意暴露以下过程：

### 10.1 至少出现一次不完美结果

不要预先把 Prompt 优化到一遍完美。

最好让 v1 合理但存在：

- 一处表述过度；
- 一处遗漏；
- 一处格式不理想。

然后现场通过反馈修正。

### 10.2 强调“先看 Agent 做了什么”

学员要观察：

- 它读了哪些文件；
- 它新建了什么；
- 它是否修改原文件；
- 它声称的事实是否有来源。

### 10.3 不把提示词变成密码

讲师不强调“必须照抄这句话才成功”。

同一个任务允许几种自然语言表达，只要满足目标 / 输入 / 约束 / 输出即可。

### 10.4 遇到失败就把失败当教材

如果 WorkBuddy：

- 找错文件；
- 生成格式异常；
- 理解有偏差；
- 编造信息；

优先展示“怎么纠正”，而不是悄悄换一个已经跑好的结果。

```text
   │  ├─ 第一次培训实操手册.md
   │  └─ L1通关卡.md
   │
   └─ instructor/
      ├─ 讲师手册.md
      ├─ 标准事实与验收表.md
      ├─ L2演示脚本.md
      └─ reset/               # 必要时用于恢复干净练习目录
```

如需要给同事直接分发，可在正式验收后额外生成：

`WorkBuddy-L1-Lab.zip`

压缩包应只包含学员需要的 Lab / 学员说明，不包含 instructor 标准答案。

## 12. 后续实施顺序

### Phase 1 — Design Freeze（当前）

本文件接受审阅并完成必要修改。

### Phase 2 — Material Build

原创并落盘：

- 项目背景；
- 交接记录；
- 四份访谈；
- Excel；
- 图表 / 截图；
- 参考简报样例。

材料制作重点不是“丰富”，而是让每个教学点都有可观察证据。

### Phase 3 — Learning Pack

制作：

- 学员逐步实操手册；
- L1 通关卡；
- 讲师手册；
- 标准事实 / 验收表；
- L2 Demo 脚本。

### Phase 4 — Dry Run / Validation

从一个干净目录完整模拟：

```text
下载 / 解压
→ WorkBuddy 打开 Lab
→ Exercise 0～6
→ v1 / v2 检查
→ 新建第二 Task
→ 讲师 L2 Demo
```

重点检查：

- 是否存在必须预装 Python / npm 才能完成的步骤；
- 是否有隐藏依赖；
- 学员是否会误读讲师答案；
- 输出目录是否清楚；
- 每一步是否能在不懂技术术语的情况下完成；
- 某一步失败后是否容易 reset。

## 13. Design Acceptance Questions

进入 Phase 2 前建议只裁决以下问题：

1. 是否接受“新岚汽车渠道研究”作为连续案例主场景；
2. 是否接受 Exercise 0～6 的顺序与深度；
3. 是否接受第一次培训不引入项目级 Skill / CODEBUDDY.md 等隐藏能力；
4. 是否接受“参考样例 → v1 → review → v2”作为第一次培训高潮；
5. L2 Demo 最终更偏向“短研究报告”还是“PPT”，可在 Phase 3 前再定，不阻塞 Phase 2 素材制作。
