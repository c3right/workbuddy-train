## 1. 为什么要做这套培训

培训对象是一家小型咨询公司的同事，岗位以研究员为主，同时包括行政和数据分析岗位。

设计起点非常明确：

1. 大多数学员此前对 AI 的使用经验，基本限于 DeepSeek 等大模型网站的网页聊天；
2. 不能预设大家理解 Agent、Skill、Context、API 等概念；
3. Git、CLI、subagent 等内容明确超纲，第一次培训不能碰；
4. 培训重点不是“介绍 WorkBuddy 有哪些按钮”，而是让完全没用过 Agent 的同事先建立一个最简单、可操作的心智模型；
5. 第一次培训只做两件事：
   - **认知重塑**：从“AI = 网页聊天”迁移到“AI 可以围绕真实工作目录持续做事”；
   - **L1 工具跑起来**：让学员亲手完成一次“理解资料 → 做任务 → 生成文件 → 检查 → 修改”的完整闭环；
6. 更完整的业务任务（L2）只由讲师演示，不要求全员在第一次培训时做到。

这里最重要的设计边界是：

> **第一次培训先打破窗户纸，不急着建立完整的 Agent 工程方法论。**

后续 Dry Run 虽然验证了人工 Gate、证据控制、阶段授权等更深层方法的重要性，但这些主要留在讲师侧，不继续加重小白的第一张心智地图。

## 2. 最初参考了什么

课程设计不是从 WorkBuddy 功能清单倒推，而是先寻找“适合非技术用户一步一步实操”的教学范式。

### 2.1 Carl Vellotti｜Claude Code for Everyone

Repository:

- https://github.com/carlvellotti/claude-code-everyone-course

这是第一课最重要的结构参考。

真正借鉴的不是 Claude Code 技术栈，而是它的教学机制：

1. 一个连续业务故事贯穿多节课；
2. 学员拿到一个完整项目目录，而不是孤立 Prompt；
3. 先探索项目，再开始做事；
4. 单文件提取 → 文件夹综合 → 套模板 → 图片 → 进一步任务，能力逐步出现；
5. 每一步真的生成文件；
6. 前一步的成果成为后一步的输入；
7. 学员是在“推进一个工作”，而不是“试几个 AI 功能”。

原项目的 Basecamp Coffee 故事采用“你刚接手前任留下的烂摊子”这一叙事。这个机制后来直接启发了“新岚汽车渠道研究项目”的接手场景。

### 2.2 Tencent WorkBuddy 官方高效使用建议

课程中明确希望体现这些原则，但不是单独讲成“八条技巧”，而是让学员在练习中自然经历：

- 清晰表达：做什么 + 有什么 + 怎么样；
- 小步快跑：一次完成一件事；
- 第一版不是终点，多轮调整；
- 给例子比抽象要求更有效；
- 不同任务使用不同 Task；
- 重要成果保留版本，可回退。

### 2.3 WorkBuddyGuide / WorkBuddy 社区材料

用于辅助理解 WorkBuddy 的项目目录、文件型任务和入门使用方式。

### 2.4 版权与原创边界

Carl 的课程用于参考教学结构，不翻译、改名或重新分发其 Basecamp Coffee 原始素材。

本仓库的：

- 公司；
- 人物；
- 访谈；
- 数字；
- Excel；
- 图片；
- DOCX 样例；

均重新原创为虚构教学材料。

## 3. 为什么最终选“新岚汽车渠道研究项目”

设计过程中需要一个能同时满足以下条件的主场景：

- 对公司研究员高度贴近；
- 行政岗位也看得懂；
- 数据岗位能看到 Excel / 图表如何进入 Agent 工作；
- 不需要汽车专业知识才能参加培训；
- 能自然出现“交接混乱、事实与观点混杂、不同区域说法不同、数据口径未确认”等真实研究问题；
- 能支持多步骤工作，而不是一个 Prompt 直接完成。

最终确定：

> **你是一名刚加入项目组的研究员，临时接手“新岚汽车渠道研究项目”。前任被调走，留下一批项目背景、交接记录、区域访谈、Excel、图片和历史简报。周五要开阶段会，你要先把项目接住。**

这个故事既能制造真实动机，又能让每个练习都有业务意义。

## 4. 第一课的核心心智地图如何形成

第一版设计曾包含较完整的 Agent 工作方法，但用户明确要求第一次培训继续保持简单。

最终学员侧保留：

```text
先选对工作目录
→ 让 Agent 先看懂资料
→ 把大工作拆成小任务
→ 说清楚：做什么 / 有什么 / 怎么样
→ 让 Agent 生成或修改真实文件
→ 人检查事实、逻辑和边界
→ 具体指出问题，继续改
→ 重要文件保留 v1 / v2
→ 换了一件事，就换一个 Task
```

培训结束时进一步压缩为五句话：

1. 先把工作目录给对；
2. 先让它看懂，再让它做；
3. 大任务拆小步，一次推进一件事；
4. 第一版只是起点，人要检查并具体反馈；
5. 重要成果保留版本；明显换任务就换 Task。

刻意不加入：

- token / context window；
- Agent 架构；
- 证据治理理论；
- Skill；
- Connector；
- API；
- Git；
- CLI；
- subagent；
- Python/npm。

原则：

> **后台方法可以严，前台教学不要重。**

## 5. Exercise 0—6 为什么这样设计

### Exercise 0｜先看看这是个什么项目

目的不是教目录命令，而是第一次让学员感受到：

> WorkBuddy 会真的进入这个项目理解资料，而不是只在聊天框里泛泛回答。

早期版本的 Prompt 更像“只查看目录，不修改文件”。Dry Run 后一度想进一步限制为“只看目录和文件名，不读正文”，但这被认为不符合真实工作习惯。

最终改成自然表达：

> “我刚接手这个项目，你先帮我看看现在大概是什么情况……”

关键变化：

- 不用人为限制 Agent 只能看目录；
- 项目包本身做得足够真实；
- 即使 Agent 为了理解项目打开少量背景文件，也不破坏教学目标。

### Exercise 1｜先把项目背景弄明白

目的：

- 先建立共同理解；
- 让学员接受“现在还不能判断”也是有效回答；
- 明确项目此时只做问题识别，不急着给最终方案；
- 知道样本不能代表全国；
- 知道客户假设不等于研究结论。

### Exercise 2｜单文件：从乱材料里提取有用信息

输入：

- 前任的项目交接记录。

输出：

- `03-output/项目交接整理_v1.md`

任务要求把混乱材料整理成：

- 已知事实；
- 明确待办；
- 项目风险；
- 待确认事项。

教学重点：

- “摘要”不是唯一用法，可以按工作目的提取；
- Agent 不应该替人补负责人、日期和无出处数字；
- 个人判断和事实要分开；
- 开始真正生成工作文件。

### Exercise 3｜整个文件夹：不是拼摘要，而是找模式

输入：

- 四份区域访谈。

输出：

- `03-output/区域访谈综合_v1.md`

目标：

- 找共性；
- 找差异；
- 找冲突；
- 找待验证问题。

这一步后来成为 Dry Run 中最重要的质量观察点：Agent 容易把“多个区域各有一位受访者提到某事”升级为“跨区域共性”，即使区域内部本身存在相反意见。

因此后来加了一个浅层但高价值的提醒：

> 如果同一区域内部自己就有不同说法，也保留下来，不要为了总结强行合成一个观点。

### Exercise 4｜给一个好样例，比说十句“专业一点”更有效

输入：

- 前面两个中间成果；
- 一份与新岚汽车业务内容无关的历史内部简报样例。

输出：

- `内部项目简报_v1.docx`

目的：

- 示范参考样例不仅能提供事实，也能提供结构、信息密度和表达方式；
- 不需要用几十条抽象要求描述“专业”；
- 让学员感受到 Context 质量影响输出质量。

### Exercise 5｜第一版不是终点：Review → v2

学员先看 v1，再给具体反馈。

要求：

- 保留 v1；
- 新建 v2；
- 不能说“再专业一点”这种模糊反馈；
- 应指出具体问题，如判断过度、遗漏区域差异、待验证事项不足等。

这一步是第一次培训的高潮，因为它把“AI 第一版不是答案”变成可见操作。

### Exercise 6｜换任务，换一个 Task

安排一个和主线交付明显不同的小任务：

- 单独分析区域经营指标图片。

教学重点：

- 同一工作继续在原 Task；
- 明显换了一件事，新建 Task；
- 不需要讲 context window / token，就能先建立正确习惯。

## 6. L2 为什么最终选择“短研究报告”

早期曾考虑 PPT，但最终用户明确决定不用 PPT。

原因：

1. 第一次培训的目的不是验证 WorkBuddy 的 PPT 生成能力；
2. PPT 会引入排版、美术、导出兼容性等无关变量；
3. L2 真正要展示的是：
   - Plan；
   - 多类型资料；
   - 中间分析；
   - 人工把关；
   - 最终研究判断；
   - Review；
   - v2。

因此 L2 最终固定为：

```text
完整业务问题
→ Plan
→ 人工确认
→ 证据矩阵
→ 人工 Gate
→ 短研究报告 v1
→ Review
→ v2
```

L2 只由讲师演示。

## 8. Dry Run 真正验证了什么

### 8.1 流程可跑通

最核心的验证不是某个模型输出多漂亮，而是：

> 一个从网页聊天转来的小白，确实可以围绕一个项目目录，逐步完成“理解 → 提取 → 综合 → 生成 → Review → v2”。

### 8.2 模型差异存在，不要把所有问题写进 Prompt

`hy4 preview` 在实跑中表现出较强主动性：

- Exercise 0 会主动多读一些材料；
- Plan 后在得到“继续”授权时会倾向继续执行；
- 综合时可能主动构造更强的模式判断。

这些可能和具体模型能力、主动性、指令遵循相关。

因此后续形成一个非常重要的课程设计原则：

> **不要因为一个模型的一次表现，就不断给学员 Prompt 加补丁。**

先区分：

- 模型差异；
- 指令遵循差异；
- Agent 工作本身普遍存在的风险。

只把跨模型、真正影响工作方法的东西固化进培训。

### 8.3 中间产物也需要检查

L2 证据矩阵不是“生成了就一定正确”。

人工 Gate 发现过：

- 个别受访者观点被放大成跨区模式；
- 口头估计容易被写得太实。

这证明：

> 重要任务不是只有最终稿要验收，中间分析也可能需要人工看一眼。

但这一点没有被扩展成复杂理论讲给第一次培训学员，只放在 L2 和讲师后台。

### 8.4 Review 不只是润色

v1 → v2 最有价值的变化，不是文字变漂亮，而是：

- 判断强度被修正；
- 区域证据重新并列；
- “证据不足”不再被误写成“假设未获支持”；
- 下一步验证更具体。

因此后续讲师手册明确：

> Review 首先看事实、逻辑、边界和判断依据，其次才是文字。

## 9. Post-Phase-4：为什么又做了一轮“沉浸感”修订

真实运行后发现，项目虽然功能上可用，但仍有一些“培训痕迹”会破坏代入感。

例如：

- 目录名 `WorkBuddy-L1-Lab` 一眼就告诉 Agent 这是实验；
- 材料正文存在“教学用虚构材料”“本次培训”“学员”等字样；
- 某些 Prompt 太像 AI 生成的规格书；
- Exercise 0 如果硬写“只准看目录名，不准打开文件”反而不符合真人工作习惯。

用户提出的原则非常明确：

> **做戏做全套。越逼真越好。**

因此做了 Immersion Pass：

1. 学员实际工作目录改名为：
   - `新岚汽车渠道研究项目/`
2. Lab 内部清理“教学 / 虚构 / 学员 / WorkBuddy L1”等字样；
3. 虚构、版权和培训说明移到 Lab 外部治理文档；
4. Excel、图片、历史简报样例同步清理培训痕迹；
5. Exercise 0 改回真人自然说法，而不是人为技术限制；
6. Exercise 0—6、L2 Prompt 全部做自然语言化；
7. 讲师侧明确：
   - 最佳实践不等于机器指令腔；
   - Prompt 可以完整，但要像一个工作思路清楚的同事在交代任务。

最终 Prompt 的判断标准：

1. 真人会不会这么说；
2. 工作要求有没有说清楚；
3. 如果删掉某句话会明显增加跑偏风险，那就保留。

不是追求“越短越自然”，而是：

> **自然但专业。**

## 10. Binary Asset Incident：PNG 损坏及修复

Immersion Pass 后，`区域经营指标截图.png` 在 GitHub 网页预览正常，但下载后本地图像查看器无法打开。

WorkBuddy 报告：

- PNG IDAT 数据尾部截断；
- zlib 校验失败；
- 容错解码可恢复绝大部分像素。

后续检查确认：

- 远端损坏 blob 与本地正常源文件字节不一致；
- 使用本地重新校验通过的 PNG 替换远端；
- 正常文件 Git blob SHA:
  - `223889a30ca67acfe1cbb89898f9c4c972de5415`
- 修复 commit:
  - `c2d16d0fe0b7f05f0f0ef16bd0f53c81b265394c`

这件事留下一个实现层经验：

> **二进制培训素材不能只看 GitHub 在线预览；正式分发前要验证“实际下载后能否正常打开”。**

后续若制作 ZIP、Excel、DOCX、PNG 等分发包，应把下载后完整性检查纳入最终验收。

## 11. 当前不可轻易回退的设计决策

未来会话修改第一课时，优先保留以下基线，除非用户明确重新打开这些议题。

### 11.1 学员心智地图保持简单

不要把下面这些继续塞回第一次培训：

- 证据升级；
- Gate 理论；
- error propagation；
- eval；
- benchmark；
- Agent architecture。

这些可以存在于讲师后台或后续课程。

### 11.2 第一课不是 WorkBuddy 功能大全

课程的中心永远是：

> **怎样带着 Agent 把一件真实工作一步一步做出来。**

而不是：

> WorkBuddy 有多少功能。

### 11.3 不引入 Git / CLI / subagent / API / Python/npm

第一次培训继续保持非技术用户可完成。

### 11.4 不追求“一轮完美”

v1 → Review → v2 是课程关键体验，不要为了现场顺滑而把案例和 Prompt 调到一次完美。

### 11.5 Lab 必须像真实项目

学员打开的项目目录中，不放答案、讲师提示、培训标签和明显教学后台。

### 11.6 Prompt 保持自然

示范最佳实践，但不要示范“AI 专用咒语”。

### 11.7 模型表现不是课程真理

换模型后允许输出表现变化。课程依赖：

- 阶段设计；
- 人工验收；
- 版本保留；

而不是依赖某一个模型刚好表现完美。
