# 第二次培训候选方案｜把重复工作沉淀成自己的第一个 Skill

> Status: **DESIGN PROPOSAL / NOT YET IMPLEMENTED**
>
> Purpose: 为后续会话提供可直接继续设计与实施的详细基线。当前只完成方案落盘，不代表已经制作素材、学员手册或完成 WorkBuddy 实跑。
>
> Relationship: 本方案必须继承第一次培训的教学逻辑，而不是另起一套“技术教程”。

---

## 1. 一句话目标

第一次培训解决：

> **AI 不只是网页聊天；WorkBuddy 可以围绕真实项目目录，和我一起把工作一步一步做出来。**

第二次培训建议只再跨一层：

> **有些工作方法我总在重复讲，可以把它教给 WorkBuddy，做成以后能重复使用的 Skill。**

不把第二课讲成：

- Skill 文件格式课；
- YAML 语法课；
- Agent 工程课；
- 自动化开发课。

第二课仍然面向同一批非技术同事，核心是理解“把重复做法沉淀成可复用能力”。

---

## 2. 为什么 Skill 适合作为第一课之后的下一步

第一课已经让学员经历：

- 给项目目录；
- 让 Agent 看懂材料；
- 单文件提取；
- 多文件综合；
- 给参考样例；
- v1 → Review → v2；
- 明显换任务时换 Task。

学员下一步最自然会碰到一个问题：

> “我每次做访谈综合，为什么都要重新说一遍这些要求？”

例如反复提醒：

- 个人观点不要写成事实；
- 同一区域内部有分歧就保留；
- 样本不能外推全国；
- 先找共性、差异、冲突和待验证；
- 无出处数字不能写实；
- 不要把相关关系直接写成因果。

这时 Skill 不再是一个抽象名词，而是一个解决真实重复劳动的办法。

因此第二课的概念入口应该是：

> **先重复一次 → 感受到麻烦 → 再把这套方法存下来。**

而不是：

> “今天我们学习 Skill。Skill 的目录结构是……”

---

## 3. 建议继续使用“研究员成长故事”

为了保持系列课连续性，建议继续第一课的人物设定。

破冰故事可以是：

> 你已经来公司几周了。
>
> 新岚项目结束后，你又陆续接了几个项目。每次做到访谈综合，你都会跟 WorkBuddy 重复说：
>
> “观点和事实分开”“同一个区域有不同意见要保留”“样本不能直接推全国”“先找共性和差异”……
>
> 说到第三次，你突然觉得：
>
> **这些不是某一个项目的要求，而是我以后做访谈研究都想遵守的工作方法。能不能只教 WorkBuddy 一次？**
>
> 这就是今天要做的事。

这个故事让 Skill 的出现有业务动机，而不是为了学功能而学功能。

---

## 4. 第一个 Skill 建议做什么

首选：

> **访谈材料综合 Skill**

建议能力边界：

输入：

- 一组访谈纪要、访谈摘要或会议访谈材料。

输出：

- 多个材料反复出现的问题；
- 区域 / 对象之间的明显差异；
- 相互矛盾或不同说法；
- 当前证据不足、需要继续验证的问题。

基本规则：

- 事实 / 访谈观点 / 项目组判断分开；
- 单一受访者观点不能自动升级成区域共性；
- 同一区域内部意见不同要保留；
- 未提及不等于不存在；
- 无出处数字不写成确定事实；
- 样本不能随意外推总体；
- 同时出现不等于因果。

### 为什么选这个 Skill

1. 和第一课 Exercise 3 无缝衔接；
2. 研究员能立即理解复用价值；
3. 行政 / 数据岗也能理解“把重复工作规则存起来”的概念；
4. 不需要写代码；
5. 不依赖脚本；
6. 输出很容易人工看懂；
7. 很适合做“无 Skill vs 有 Skill”的对照；
8. 可以通过换一套全新材料验证是否真的可复用。

### 不建议第一个 Skill 做什么

不建议第一课后立刻做：

- 万能研究 Skill；
- 自动生成完整咨询报告 Skill；
- 带 Python 脚本的数据 Skill；
- 自动联网研究 Skill；
- 多 Skill 串联；
- subagent；
- Connector / MCP；
- 自动化流水线。

第一个 Skill 越窄越容易让小白真正看懂“复用”的价值。

---

## 5. 第二课最重要的教学主线

建议保持和第一课一样简单：

```text
先用普通方式做一次
↓
发现自己总在重复同一套要求
↓
把这些要求整理成“我的工作方法”
↓
让 WorkBuddy 帮我创建 Skill
↓
第一次试用
↓
自己检查哪里不对
↓
修改 Skill
↓
换一套新材料再试
↓
确认它真的能复用
```

这其实就是第一课的：

> v1 → 人检查 → 具体反馈 → v2

提升到 Skill 层面。

因此第二课并不是突然进入技术层，而是把已经学会的 Review 思维继续用在“可复用能力”上。

---

## 6. 建议的 Exercise 结构

当前建议设计为 Exercise 0—7。后续实施时可以再压缩，但不要一开始扩成复杂课程。

### Exercise 0｜先遇到“重复”

给学员一组新的访谈材料。

让学员仍用普通 Prompt 做一次综合。

这里故意要求他们像第一课一样，把熟悉的规则再次说出来。

目的：

> 先让学员感受到“我又在重复这些要求”。

不要在这一关提前讲 Skill。

---

### Exercise 1｜把重复要求找出来

让 WorkBuddy 帮忙回看刚才这次任务，问：

> “刚才这些要求里，哪些其实不是这个项目独有，而是我以后做访谈综合也会一直希望你遵守的？”

让学员得到一份很短的“稳定工作方法”。

这一步是在做 Skill 的 intent capture，但学员不需要知道这个术语。

预期整理出：

- 什么时候适用；
- 希望它做什么；
- 有哪些边界；
- 输出长什么样。

---

### Exercise 2｜让 WorkBuddy 创建第一个 Skill

用自然语言告诉 WorkBuddy：

> “把刚才这套以后会反复用的做法，帮我整理成一个 Skill。”

在 WorkBuddy 当前真实能力允许的情况下，优先让产品自己创建 / 安装项目级 Skill，而不是学员手工建目录和写 YAML。

这里需要在真正实施前再次核验 WorkBuddy 当前版本的：

- Skill 创建入口；
- 项目级 Skill 保存位置；
- 是否支持自然语言创建；
- 如何查看 / 编辑；
- 如何确认已加载。

**不要直接假设 Claude Code 的路径和 WorkBuddy 完全一样。**

如果 WorkBuddy 需要打开 Skill 文件，讲师可以带着看，但只讲三件事：

- 名字：这项能力叫什么；
- description / 说明：什么时候该用；
- 正文：用了以后要怎么做。

暂时不教 YAML 语法。

---

### Exercise 3｜第一次使用 Skill

仍用刚才那组材料，重新发一个更自然、更短的任务：

> “把这几份访谈综合一下，帮我找共性、差异、冲突和后面要验证的问题。”

观察：

- WorkBuddy 是否识别并使用 Skill；
- 输出是否自动遵守前面沉淀的规则；
- 学员是不是不用再把所有边界重新说一遍。

这里第一次让学员形成直觉：

> **Skill 不是“让模型更聪明”，而是让一套稳定做法不必每次重讲。**

---

### Exercise 4｜人检查 Skill v1

不要假设第一个 Skill 完美。

检查：

- 有没有触发过度；
- 有没有规则太死；
- 有没有遗漏关键边界；
- 输出是不是太长；
- 有没有把某个案例特有规则误写成通用规则。

例如一个高价值问题：

> “这个 Skill 里是不是混进了‘新岚汽车’这种只属于第一课项目的东西？”

让学员理解：

> **可复用 Skill 要抽掉项目偶然性，只保留稳定方法。**

---

### Exercise 5｜修改 Skill → v2

给具体反馈，让 WorkBuddy 修改 Skill。

例如：

- description 更明确；
- 去掉某个项目专属要求；
- 增加“同一区域内部不同说法要保留”；
- 输出结构压缩；
- 明确不做因果推断。

这里继续沿用第一课习惯：

> 第一版不是终点。

Skill 本身也需要 Review。

---

### Exercise 6｜换一套完全新的材料做真正测试

这是第二课的关键高潮。

不能只拿创建 Skill 时见过的材料测试。

必须准备一个**全新的项目 / 全新的访谈包**，最好换行业、换角色、换业务问题。

例如候选：

- 新能源储能渠道访谈；
- 连锁零售门店经营访谈；
- 企业软件客户流失访谈；
- 售后服务网络访谈。

要求：

- 仍然是多份访谈；
- 证据结构类似；
- 业务内容完全不同；
- 不出现“新岚汽车”的任何事实；
- 至少有内部不同意见、单一受访者观点和待验证问题。

只给一个自然任务：

> “帮我把这组访谈综合一下。”

看 Skill 是否还能正常工作。

这一步要让学员真正意识到：

> **我做的不是‘新岚汽车 Prompt’，而是一套可以跨项目复用的工作方法。**

---

### Exercise 7｜收口：什么时候值得做 Skill

不要讲复杂分类。

只让学员记住：

适合做 Skill：

- 我已经重复做过几次；
- 每次都要重复说类似规则；
- 做法相对稳定；
- 我希望以后少说一遍，但结果保持一致。

不一定适合做 Skill：

- 一次性任务；
- 规则还没想清楚；
- 每次做法变化很大；
- 只是为了把一个超长 Prompt 换个地方存。

最后一句：

> **先把工作做顺，再把稳定做法沉淀成 Skill。**

---

## 7. 第二课学员侧最简心智地图

建议只保留：

```text
先把一件事做顺
↓
发现哪些要求总在重复
↓
把稳定方法做成 Skill
↓
用真实任务试
↓
不满意就改 Skill
↓
换一套新材料再试
```

不要给第一次接触 Skill 的学员引入：

- progressive disclosure；
- eval framework；
- benchmark；
- assertion；
- token budget；
- Skill precedence；
- context fork；
- subagent；
- scripts；
- CLI 安装；
- Git 分发。

这些可以后续逐层出现。

---

## 8. 教学上如何解释 Skill

建议不要从文件结构开始。

先用最直观的一句话：

> **Skill 就是把一套你经常重复的工作方法，教给 WorkBuddy，让它以后在合适的时候拿出来用。**

再补三个最小组成：

1. **叫什么**；
2. **什么时候用**；
3. **用了以后怎么做**。

到这里就够完成第二课。

如果学员打开 Skill 文件，讲师再补充：

> “背后其实就是一个可以被 Agent 读取的说明文件；以后复杂了还可以带模板、参考资料甚至脚本，但今天先不碰。”

## 9. 建议的素材包结构

建议继续采用“下载 ZIP → 解压 → 在 WorkBuddy 里选项目目录 → 一步一步走”的模式。

候选目录：

```text
第二课-访谈综合Skill/
│
├─ 00-项目背景/
│  └─ 01-任务说明.md
│
├─ 01-第一次练习/
│  ├─ 访谈A.md
│  ├─ 访谈B.md
│  ├─ 访谈C.md
│  └─ 访谈D.md
│
├─ 02-迁移测试/
│  ├─ 新项目背景.md
│  ├─ 访谈A.md
│  ├─ 访谈B.md
│  ├─ 访谈C.md
│  └─ 访谈D.md
│
└─ 03-output/
   └─ README.md
```

实际实现时，如果 WorkBuddy 的项目级 Skill 会自动生成隐藏目录，应让它由产品自然创建，不提前把“答案 Skill”放进学员包。

讲师标准答案 / 参考 Skill 放在：

```text
instructor/
└─ second-training/
   ├─ 参考Skill/
   ├─ 标准事实与验收表.md
   └─ 讲师脚本.md
```

不要放进学员工作目录，避免 Agent 直接读到答案。

## 10. 是否继续用新岚汽车世界观

推荐：

> **故事连续，但测试材料必须跨项目。**

即：

- 开场仍然是第一课那个研究员，工作了几周；
- 创建 Skill 的动机来自第一课学过的访谈综合方法；
- 真正的迁移测试换一个新行业。

这样既有系列课连续感，又能证明 Skill 是“可复用方法”而不是“保存了新岚汽车答案”。

---

## 11. 第二课不要急着加入 reference / template / script

第一个 Skill 建议尽量保持最小：

```text
skill-name/
└─ SKILL.md
```

如果 Skill v2 确实需要一个稳定输出模板，可以作为第二课后半段或第三课自然加入：

```text
skill-name/
├─ SKILL.md
└─ references/
   └─ 输出结构.md
```

但不建议第一次开发 Skill 就出现：

- scripts/；
- evals/；
- assets/；
- 外部工具；
- API；
- shell。

原因：

> 第二课要让学员先理解“工作方法可复用”，而不是理解“Skill 是一个复杂软件包”。

## 13. 除了“自己开发 Skill”，后续还能做哪些 ZIP 实操课

以下都适合沿用第一课的形式：

> 下载一个项目包 → 在 WorkBuddy 里选为工作目录 → 按步骤推进 → 真正生成成果。

### 候选 A｜从优秀样本提炼 Skill

素材：

```text
历史优秀报告/
├─ 报告A.docx
├─ 报告B.docx
└─ 报告C.docx

新任务材料/
└─ ...
```

过程：

1. 先分析几份优秀成果共同好在哪；
2. 提取稳定方法；
3. 做成 Skill；
4. 用新任务测试。

这个非常适合咨询公司，因为它展示：

> **Skill 可以从团队优秀经验中提炼，而不是凭空写规则。**

建议作为第三课高优先候选。

---

### 候选 B｜项目周报 / 阶段汇报包

素材：

- 上周周报；
- 本周会议纪要；
- 项目进度表；
- 若干零散更新；
- 固定汇报模板。

目标：

## 15. 第二课的讲师后台原则

### 15.1 不要把 Skill 神化

不要说：

> “装了 Skill，以后 AI 就自动正确。”

正确表达：

> “Skill 是把稳定要求提前写好，减少重复说明；输出仍然需要人检查。”

### 15.2 不要为了教学做一个过度复杂 Skill

如果一个 SKILL.md 就能解决，不要硬塞 references / scripts。

### 15.3 不要做隐藏魔法

学员应该知道：

- Skill 是谁创建的；
- Skill 大概写了什么；
- 为什么修改后结果改变。

不要偷偷预置一个高质量 Skill 再假装是现场生成。

### 15.4 不针对单一模型过度加规则

沿用第一课经验。

如果某模型：

- 不自动触发；
- 太主动触发；
- 生成 Skill 过长；

优先区分产品 / 模型行为，不要马上把所有偶发问题变成学员规则。

### 15.5 Skill 的验收重点是“迁移”

第二课最重要的验收不是：

> 同一套材料做第二遍更好。

而是：

> 换了业务材料以后，这套方法还能工作。

## 16. 实现前必须重新核验的 WorkBuddy 产品事实

第二课真正实施前，必须以当时最新 WorkBuddy 官方文档 / 实机为准确认：

1. WorkBuddy 当前支持哪些 Skill 存放位置；
2. 项目级 Skill 的真实目录约定；
3. 是否支持自然语言创建 Skill；
4. 是否支持 UI 查看 / 编辑 / 删除 / 禁用；
5. Skill 的触发机制；
6. Skill 是否需要重载或新 Task 生效；
7. 项目级与个人级 Skill 的范围；
8. ZIP 分发时 Skill 是否应预置；
9. 是否存在 WorkBuddy 自带 Skill creator / 生成能力；
10. 不同模型对 Skill 触发的一致性。

不要直接把 Claude Code 的：

- `.claude/skills/`；
- slash command；
- CLI；

照搬成 WorkBuddy 事实。

## 17. 建议的实施 Phase

### Phase S1｜Design Freeze

需要确认：

1. 第一 Skill 是否就用“访谈材料综合”；
2. 是否采用“同一研究员成长故事 + 新项目迁移测试”；
3. 第二课是全员跟做，还是前半全员、后半讲师 Demo；
4. 是否只做最小 Skill，不加入 references；
5. 是否需要给学员一个第二套测试材料包。

### Phase S2｜Material Build

制作：

- 第一次练习访谈包；
- 全新迁移测试访谈包；
- 讲师标准事实；
- Skill v1 / v2 参考答案；
- 必要的输出模板。

### Phase S3｜Learning Pack

制作：

- 第二次培训学员实操手册；
- Skill 最简心智卡；
- 讲师手册；
- 标准事实与验收表；
- reset / recovery 说明。

### Phase S4｜Dry Run

至少使用：

- 一个 WorkBuddy 当前主流模型；
- 干净目录；
- 从零创建 Skill；
- 同材料试用；
- Skill 修改；
- 新材料迁移测试。

重点记录：

- Skill 是否稳定被发现 / 触发；
- 是否有模型依赖；
- 是否把项目专属规则误写进通用 Skill；
- 新材料是否能迁移；
- 学员是否必须理解技术目录才能完成；
- 是否出现隐藏依赖。

最终仍建议采用：

> **PASS / PASS WITH LIGHTWEIGHT REVISIONS / RETURN**

而不是凭一次演示感觉判断。

## 18. 第二课成功标准

学员不需要能解释 Skill 技术机制。

只要能做到：

- [ ] 知道什么样的重复工作值得沉淀；
- [ ] 能把一套稳定要求说清楚；
- [ ] 能让 WorkBuddy 创建一个简单 Skill；
- [ ] 知道 Skill 大概包含“什么时候用 / 怎么做”；
- [ ] 能用真实任务试一次；
- [ ] 能指出一个问题并修改 Skill；
- [ ] 能换一套新材料再验证；
- [ ] 知道有 Skill 也仍要人工检查。

就算通过。
